# Conveyor — session handoff

Read this first when resuming work. It captures everything that is not obvious from the
code: state, conventions, gotchas, and exactly what to build next. `PLAN.md` is the full
roadmap (§21 has per-milestone implementation notes); this file is the operational summary.

## 1. What Conveyor is

A self-hosted Bazel Build Event Service (BES) server with a Phoenix LiveView UI, MIT licensed.
Bazel clients point `--bes_backend` at the gRPC endpoint; every build appears live with its
log, timeline, targets, tests, metrics, and free-form tags from `--build_metadata`, plus a
dashboard (success rate, p50/p90/p99 per segment, cache hit rate, failures, tests).

Stack: Elixir 1.20 / OTP 29, Phoenix 1.8 + LiveView 1.2, PostgreSQL 17 (dev container),
elixir-grpc 1.0 (`grpc_server` + `grpc`, Cowboy adapter), `protobuf` 0.17, Oban 2.24,
excoveralls, Tailwind v4 (daisyUI plugin present but app components are hand-written).

## 4. Running things locally

```sh
docker compose -f docker-compose.dev.yml up -d      # Postgres on 127.0.0.1:5440 (user/pass postgres)
mix setup                                           # deps, db create+migrate, assets
PORT=4100 mix phx.server                            # web :4100 (port 4000 is taken by another project on this machine), gRPC :1985
```

- Dev ingest auth is `:none` (everything lands in project `default`); set `BES_INGEST_AUTH=api_key` to require keys.
- Restart flow used all session: `pkill -f "mix phx.server"`, wait until ports 1985/4100 are free, start again. Two servers cannot share the gRPC port.
- Real build: from `test/fixtures/workspace`:
  `bazel test //app:pass_test //lib:greeting --action_env=NONCE=$RANDOM --bes_backend=grpc://localhost:1985 --bes_results_url=http://localhost:4100/invocation/ --build_metadata=USER=$USER --build_metadata=CI=false`
- Replay fixtures (no Bazel needed), with connection-drop chaos and the persistence oracle:
  `mix conveyor.replay test/fixtures/bep/*.bep --repeat 100 --concurrency 200 --drop-after 20 --verify`
- Realistic browsing data: `mix conveyor.seed --replay 1500 --days 30 --big-log 50` (`--big-log MB` adds one CI build with a curses-style log of that size for the log viewer) replays the fixtures through the real pipeline (all tabs populated; varied users/hosts/branches/durations; starts the app without listeners, safe while the server runs; refresh the browser). Synthetic volume only: `mix conveyor.seed --invocations 5000 --days 30` (rows without events; starts only the Repo).
- Screenshots for design review: `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --screenshot=out.png --window-size=1440,1000 URL` (LiveView JS does not connect in headless screenshots; server-rendered HTML only).
- Test DB: `mix test` migrates automatically. If migrations are edited in place (they were, pre-release), rebuild: `MIX_ENV=test mix do ecto.drop, ecto.create, ecto.migrate` and `mix ecto.reset` for dev.
- Regenerate protobuf modules after changing `priv/protos/`: `priv/protos/gen.sh` (needs `protoc` and `~/.mix/escripts/protoc-gen-elixir`). `google/api`, `google/rpc`, `google/longrunning`, `google/bytestream` messages come from the `googleapis` hex dep and are NOT generated (the ByteStream *service* module is missing from the dep — hand-write a `GRPC.Service` for it when building the CAS sink).

## 6. Key design facts to keep intact

- **Acks are the durability boundary.** An event is acked only after its batch commits; Bazel resends from the last un-acked seq; `seq < expected` is acked immediately (dedup); `seq > expected` → FAILED_PRECONDITION.
- **Fencing:** every batch commit does `UPDATE invocations SET ... WHERE last_event_seq = first_seq - 1`; failure = `{:fenced, n}` → worker exits → stream fails → Bazel retries. Works across nodes without cluster locks.
- **Segment partition day = `invocations.inserted_at` date**, never `started_at` (it changes). Partitions `event_segments_YYYYMMDD` / `log_segments_YYYYMMDD` are created on boot (`Conveyor.Storage.boot/0`) and hourly; creation tolerates `duplicate_table` (boot races).
- **Targets are keyed by (label, aspect)**; `configuration_id` is an attribute (TargetConfigured carries no configuration).
- **Tags:** lowercase keys, string values; reserved keys (`status`, `id`, `project`) become `user.<key>`; ignored: build_timestamp, formatted_date, build_embed_label, command_name, protocol_name.
- **API keys:** `conveyor_<8 base32 chars>_<43 base64url>`; sha256 stored; lookup by key_id via ETS (30 s TTL, invalidated locally + via PubSub).
- **Bazel retry budget is short** (default 4 retries ≈ seconds). Docs must recommend `--build_event_upload_max_retries=10`; restarts must be fast; balancers must stop routing before a node drains.
- **Bazel copies the client env into the command line** (`--client_env=NAME=VALUE`), so scrubbing is mandatory. 2026-09-19: GitHub push protection caught real AWS keys in the recorded fixtures (the scrubber missed credential-named env vars such as `AWS_SECRET_ACCESS_KEY`; fixed with the `@env_re` rule, fixtures re-scrubbed, and the whole history rewritten with `git filter-repo --blob-callback`, same-length filler so old protobuf fixtures still decode). Before recording new fixtures, run Bazel from a shell without credentials in the environment (`env -i PATH=$PATH HOME=$HOME bazel ...`), and re-scrub with `Conveyor.Ingest.Scrub` (see the scrub test that asserts fixtures are already clean).
- **Finish lifecycle events must never start a new worker** for a finished build (it did once; worker lived until idle timeout).
- Config knobs live in `config :conveyor, Conveyor.Ingest` (auth, idle_timeout_ms, linger_ms, batch_max_events/bytes, batch_flush_ms, writer_shards, writer_flush_ms, tag_flush_ms, broadcast_interval_ms, max_unacked_events).
- **Log viewer path (any log size):** the LiveView never sends log text; `log:reset` carries the download URL, `live` and byte count; the browser's log worker streams `/invocation/:id/download/log` (chunked, `x-log-bytes` header) into a paged byte buffer with terminal emulation (`\r`, cursor-up, SGR kept) and serves only visible lines to the page. Live appends (`{:log_chunks, chunks, offset}` on the log topic → `log:append` with `offset`) splice by byte offset; appends ahead of the loaded bytes queue and trigger one delayed reload. Measured: 50 MB in 0.2 s, 127 MB RSS, filter 9 ms. `node --test assets/test/*.test.mjs` runs in precommit (Node 24 on this machine).
- **Writer hot path (M7 profiling):** a group commit writes one statement per table and column set (segments, targets, tests, actions, named sets, metrics) then one fenced `UPDATE` per batch; rows of the same invocation across batches are merged in order (one upsert must not touch a row twice). `tag_keys` rows are shared per project and must never be updated inside the group transaction (it serialized every shard on their row locks) — counts go through `Conveyor.Ingest.TagCounter` (one sorted upsert per node per second). Never index `last_event_at` (or any column the per-batch update sets): it makes every update non-HOT. Tests that assert tag counts call `TagCounter.flush()` first. DB pool: dev 20, prod `POOL_SIZE` default 40, `queue_target 1s / queue_interval 10s` (overload → latency, not errors).

### DONE 2026-09-26: raw segments write-behind (0.2.3, off by default) — next: enable on the trial

**Shipped** (`ec77107` model, `6eb9b71` code, `1b986fa` tests, `bc65441` bench): `Conveyor.RawArchive` + `Conveyor.Workers.ArchiveRaw` behind `RAW_ARCHIVE_ENABLED` (default `false`), `RAW_ARCHIVE_AFTER_HOURS` (24); the server refuses to start with the archive on and `RETENTION_RAW_DAYS*24 < after_hours + 24`. Deviations from the design text below, all deliberate: per-build jobs run on their own `archive` queue (2 slots) so a backlog never delays maintenance/rollups (the cron scheduler job enqueues one unique job per due build); candidates are bounded by the oldest existing partition through a new index on `invocations.inserted_at` (the four new columns stay unindexed); the gauge is `conveyor_raw_archive_overdue_seconds` (how long the oldest due build waited *past* the delay, recomputed at most once a minute per node) with alerts `ConveyorRawArchiveBehind` (> 6 h for 30 min) and `ConveyorRawArchiveMismatch`; a build whose segments do not match its row (`event_count`, `log_bytes`) is marked `raw_status = 'skipped'` so it never blocks a partition; the archive never touches `updated_at` (rollup staleness keys on it). Bench (docs/capacity.md ledger): ingest unchanged in a same-harness A/B; archiving 10k bench builds took 10.6 s, database per build 31.4 → 22.7 KB after the guarded drop, blob store 6.6 KB/build, oracle 10k/10k from the blobs. `mix test --only s3` (MinIO `chumti-minio`, creds from the container's `MINIO_ROOT_USER_FILE`/`MINIO_ROOT_PASSWORD_FILE`, `env -u AWS_SESSION_TOKEN`) includes `raw_archive_s3_test.exs`.
**Rollout next:** set `RAW_ARCHIVE_ENABLED=true` on the trial (add the env to `templates/conveyor.sh.tftpl` as a variable defaulting to true only after a trial window), watch the gauge fall to 0 and `conveyor_raw_archive_failures_count` stay 0 for a day, check S3 request costs, then make it the default and lower `RETENTION_RAW_DAYS` to 2. Two follow-ups worth doing: `events_page/2` decodes the whole blob per page (fine for small builds; add the `raw_index` byte-offset jsonb when the Events tab gets slow on big builds), and the S3 adapter's `exists?` is now called on every pin (one HEAD per artifact attach).


**Model results (`docs/spec/Archive.tla`, 2026-09-26) — three changes to the design below, applied before any code:**
(a) the date-only partition drop loses a finished build's segments whenever the archive lags (a store outage, or with `RETENTION_RAW_DAYS=2` a build crossing midnight gets an hour of slack): `Partitions.drop_before/1` skips a day that still holds a finished build with `raw_status = 'segments'` (`RawArchive.holds_unarchived?/1`, through a new index on `invocations.inserted_at`, which never changes so HOT is unaffected), and the oldest-unarchived gauge alerts; (b) the reference must be recorded in one transaction that pins the blob row, or a stalled archiver references a blob prune already removed; (c) a pre-existing `Blobs` race: `delete_blob/2` deleted the object after its commit, so a re-put of the same digest in between (an archive re-run after a crash, or any re-upload) got pinned and referenced and then lost its bytes — deletion now removes the object while it holds the row lock, and `pin/2` checks the object exists under the lock (`Blobs.tla` extended with re-upload; `Blobs_reupload.cfg` is the 0.2.2 code). The rule "`RETENTION_RAW_DAYS` ≥ delay + 1 day, refuse to start otherwise" stays as a sanity check; the drop guard is what makes it safe.


**Decision.** Move finished builds' raw BEP events (and logs) out of Postgres into the existing blob store after a delay, keeping every acknowledgement a Postgres commit. Do **not** shard the database yet: one database carries tens of thousands of events/s (17.5k at 0.7 vCPU, 730 WAL B/event measured), so history size, not commit rate, is the first limit. Keep the sharding seam clean (all access behind `Conveyor.Repo`, project-scoped queries, per-project rollups and blob prefixes, no cross-project SQL joins) so sharding by project group stays a contained change if a fleet ever needs 50k+ events/s sustained. Write-behind does not reduce WAL (written at ingest); it removes Postgres growth, shrinks backups, and makes raw retention long and cheap (S3 ≈ $0.023/GB-month; one object per finished build ≈ $0.50/day of PUTs at 100k builds/day; per-flush objects would cost ≈ $10/day, which is why raw bytes stay in Postgres on the hot path).

**Today's raw data.** `event_segments`/`log_segments`: daily partitions by `invocations.inserted_at` date (`Conveyor.Storage.Partitions`, created on boot and hourly; `RETENTION_RAW_DAYS` default 14 drops partitions in `PartitionMaintenance`), PK `(day, invocation_id, first_seq)`, one row per writer flush per invocation (coalesced, PLAN §24.1), `payload` = varint-delimited BEP frames (`Conveyor.Bep.Fixture` framing, the `--build_event_binary_file` format) compressed by `Invocations.compress_bep/1` (zstd + dictionary `priv/zstd/bep-1.dict`, dict id in the frame; `decompress/1` picks the dictionary). Logs: `data` = raw text chunks, plain zstd, with `byte_offset`/`line_offset` for the streaming viewer. Readers: `Invocations.raw_frames/1`, `events/1`, `events_page/2`, `log/1`, `log_segments/1`, `ConveyorWeb.DownloadController` (events download; log download streams segment by segment with the `x-log-bytes` header for the browser log worker), `Conveyor.Ingest.Verify` (oracle: contiguity, counts, decoded frames, log chain), `Conveyor.Bench`. Nothing on dashboards, lists, targets, tests or the timeline reads them. Storage: ≈ 8 KB per small build for events after the dictionary (real builds 100 KB–MB), the bulk of the ≈ 30 KB/build.

**Design.**
1. `Conveyor.Workers.ArchiveRaw` (Oban, `maintenance` queue, cron every 15 min, `unique` per invocation): selects finished builds (`stream_finished`, status final) with `raw_status = "segments"` (new column, default `"segments"`), `finished_at < now − RAW_ARCHIVE_AFTER_HOURS` (default 24) **and** `updated_at` older than two idle windows (a late lifecycle finish or a resumed stream must not race the archive; same rule as `Retention.tla`). Per build: read its event segments in `first_seq` order, concatenate the *decompressed frames* and recompress once with the dictionary (`compress_bep`), so the object is exactly a compressed `--build_event_binary_file`; the log likewise (`compress`). `Blobs.put(project, bytes, source: "raw", content_type: "application/x-bep+zstd")` (pinned from the start, no TTL) then, **in the same transaction**, `UPDATE invocations SET raw_blob = digest, log_blob = digest2, raw_status = 'archived', raw_archived_at = now WHERE id = $1 AND raw_status = 'segments'` (0 rows → another node archived it: delete the just-written blob if unreferenced, `Blobs.tla` ordering). Segment rows are **not** deleted individually; the daily partition drop stays the deletion, so set `RETENTION_RAW_DAYS` ≥ `RAW_ARCHIVE_AFTER_HOURS/24 + 1` and refuse to start with a smaller value (both knobs in `config/runtime.exs`; the defaults can become 2 days once archive is live). Chunked reads/writes (`Retry.with_backoff`, 5-minute statement timeouts like `ExecLog.store!`).
2. **References.** `raw_blob`/`log_blob` are new reference kinds: add them to `Blobs.prune_orphans/2` subqueries **and** to `Blobs.referenced?/1` (the locked re-check in `delete_blob/2`), or the nightly prune deletes archived raw data. Build retention deletes the invocation → the blobs become orphans → pruned after the grace period (already how artifacts work). Per-project blob prefixes apply unchanged.
3. **Read path.** `raw_frames/1`: `raw_blob` present → `Blobs.stream/2` → decompress → `Fixture.frames/1`; else segments (both exist during the window before the partition drop; prefer the blob when present so behaviour is stable). `events_page/2` pages by scanning frames from the blob (sequence numbers are contiguous 1..N; add a small `raw_index` jsonb of byte offsets every 1,000 frames only if the Events tab gets slow on big builds). Log: `log/1` from `log_blob`; the download controller must **stream** the decompressed log for the browser worker (logs up to 256 MB): use the zstd context API (`:zstd.context(:decompress)`, `:zstd.stream/2`, `:zstd.finish/2`, already in OTP 29's `zstd`) fed by `Blobs.stream/2` chunks, keep the `x-log-bytes` header from `invocations.log_bytes`. `log_segments/1` (offsets) is only used by the oracle and tests: derive from the row (`log_bytes`, `log_lines`) when archived. `Verify.check/2` must pass on archived builds: decoded frames == sent, `event_count`, log length == `log_bytes`; contiguity is implied by the single object.
4. **Migration**: `raw_status` (default `"segments"`), `raw_blob`, `log_blob`, `raw_archived_at` on `invocations` (nullable; never index them — the per-batch update rule). `Blobs` need no schema change.
5. **Config/metrics**: `RAW_ARCHIVE_AFTER_HOURS` (24), `RAW_ARCHIVE_ENABLED` (true), counters `conveyor_raw_archived_count`, `conveyor_raw_archived_bytes`, `conveyor_raw_archive_failures`, gauge oldest unarchived finished build age with an alert in `deploy/prometheus/alerts.yml`; docs: capacity.md (storage per build after archive), configuration.md, operations.md ("raw data lives in the blob store after a day; Events tab reads from S3").
6. **Model first** (`docs/spec/Archive.tla`, `check.sh` config): invariant *every event is in the segments or in the blob at all times* (archive writes blob + reference before any partition drop can remove the segments; drop only touches partitions older than the archive delay plus a day; archive never runs while a segment write may still come). Chaos: node dies between put and reference (the put becomes an orphan and is pruned; the next run archives again), two nodes archiving the same build (the conditional UPDATE picks one; the other deletes its blob), a late lifecycle finish after archive (marker-only batch: no segment rows; allowed).
7. **Tests**: ingest a fixture through the real pipeline (`LiveCase.ingest_fixture!`), run `ArchiveRaw`, assert `raw_frames/events/log/events_page` byte-identical before and after and `Verify.check` green; download controller streams the archived log with the same `x-log-bytes`; prune keeps raw blobs, retention makes them orphans and prune removes them; the S3 contract test (`mix test --only s3`, MinIO `chumti-minio`) for the streamed read; a bench run before/after for `storage/build` (harness `bench/run.sh`, expect event_segments to vanish from the table sizes after the job) and the dashboard unaffected.
8. **Rollout**: ship behind `RAW_ARCHIVE_ENABLED=false` in 0.2.3, enable on the trial, watch the gauge and S3 request costs, then default on; shrink `RETENTION_RAW_DAYS` default afterwards.

**Not doing (recorded):** raw bytes skipping Postgres (would need S3 or a log in the ack path); database sharding (revisit at ≈ 50k events/s sustained or when one database's WAL becomes the operational pain; the seam is described above).

### Ingest protocol in TLA+ (2026-09-23) — a real bug found and fixed

`docs/spec/Ingest.tla` + `check.sh` (TLC from `~/tla/tla2tools.jar`, Java 21 on this machine). Three configs: `fixed` (current protocol, all properties hold, 634k states), `current` (the shipped dedup rule → `Durability` violated in 7 steps), `pre_m10` (stray worker + unrecorded fenced finish → `Completes` violated, the trial's stuck builds). **The finding:** `Worker.handle_call({:push…})` acked any resend below `expected_seq` at once, but `expected_seq` advances on absorb, so after a drop and a reconnect to the same node (always, with one node or a sticky balancer) an uncommitted event was acknowledged; a failed commit (retries exhausted) then lost it with Bazel believing it stored. Fixed: ack at once only when `seq <= committed_seq`, otherwise the new connection is registered as a waiter on the batch that carries the event (`await_commit/3`); `worker_test.exs` pins it and fails against the old rule. Modelling lessons: `x' = a \/ b` parses as `(x' = a) \/ b` (parenthesize); a failed takeover keeps the reloaded state (`{:error, fresh}`), the first model looped without it; Bazel sends the finish notification once, so the model must too or the pre-M10 bug hides. Not yet deployed or tagged (0.2.1 candidate: this fix plus the dashboard commit `3237cf4`).

## 9. Testing conventions

- **Browser tests** live in `e2e/` (Playwright, Chromium): `cd e2e && npm ci && npx playwright install chromium`, then `BASE_URL=http://localhost:4100 npm test` against a seeded dev server. They caught what LiveView tests cannot: `phx-value-value` on a `<button>` is shadowed by the button's own DOM `value` (always use another suffix such as `phx-value-tag`), and they exercise the log worker and the profile timeline for real. `.github/workflows/browser.yml` runs them on every push.
- **Timeline (profile) viewer**: `assets/js/profile_worker.js` builds depth/parent/phase per event and per-action phase rows (`PHASES`), `assets/js/hooks/profile_timeline.js` renders flame rows, minimap, range zoom, keyboard, details with the action breakdown and the "where action time went" panel; `Conveyor.Profile.phase/2` is the server-side twin (`action_phases` in the summary). Seeded CI builds carry synthetic remote-execution profiles (`Conveyor.Seed.synthetic_profile/2`); no real remote-execution profile has been recorded yet, so the phase vocabulary is from Bazel's ProfilerTask names and should be checked against a real RBE profile when one is available.

- Unit tests are async; anything touching ingest workers/writers uses `Conveyor.IngestCase` (shared sandbox, gRPC on a random port, `await_worker_exit/1`) or `ConveyorWeb.LiveCase` (`ingest_fixture!/2` pushes a fixture through the real pipeline with `Ingest.push_sync/2`).
- Fixtures in `test/fixtures/bep/*.bep` (scenarios: clean_build_and_test, cached_build_and_test, build_failure, test_failure, flaky_test, analysis_failure, build_only_verbose) recorded from `test/fixtures/workspace` with `--build_event_binary_file` and `--build_event_publish_all_actions`; re-scrub with `Conveyor.Ingest.Scrub` if re-recorded.
- Query tests compare SQL and in-memory results for every operator; keep both evaluators in sync.
- LiveView tests assert on element ids (see AGENTS.md rules); stream containers need ids on every child including empty-state rows; hooks need unique ids.
- Expected error logs in failure-path tests carry `@tag :capture_log`.
